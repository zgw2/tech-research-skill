## 模块一：核心需求解构与核心约束指标
- **核心诉求**：大文件（>1GB）上传过程中抗网络抖动、页面刷新后可续传、重复文件秒传、并发分片限流。
- **关键约束与指标**：
  - 客户端计算 Hash（MD5 / SHA-256）的 CPU 占用与主线程流畅度（不能卡顿 UI）；
  - 分片粒度：建议 5MB~20MB，避免请求数过多压垮网关（HTTP 连接数上限）；
  - 存储兼容性：需支持主流对象存储（AWS S3 Multipart Upload / 阿里云 OSS 分片上传）；
  - 离线续传状态持久化机制（IndexedDB vs LocalStorage）。

## 模块二：主流方案横向决策矩阵

| 方案名称 | 核心技术原理 | 关键优势 | 劣势与隐藏成本 | 维护/学习成本 | 推荐适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **方案 1：Uppy / Simple-Uploader 等成熟开源 SDK** | 封装 WebWorker Hash + Tus 协议/S3 Multipart | 开箱即用，生态健全，支持断点重试与 UI 组件 | 包体积稍大，复杂业务定制（如加盐加密）有心智负担 | 低 ~ 中 | 绝大多数业务前台系统、中后台上传组件 |
| **方案 2：自研 WebWorker 分片 + S3 直传** | 纯原生 FileReader 分片 + WebWorker 抽样 Hash 计算 + S3 Presigned URL 直传 | 零外部臃肿依赖，定制自由度高，不占用应用服务器带宽 | 边界情况处理繁琐（网络断开重试、分片合并超时、IndexedDB 存储管理） | 高 | 超大型平台、需严格审计/防重放/极端定制架构 |
| **方案 3：第三方商业云 SDK (如七牛/腾讯云 Web SDK)** | 直连云厂商专用分片直传接口 | 稳定性好，自带 CDN 加速和转码流水线 | 与特定云厂商强绑定，迁移成本极高 | 极低 | 已经全量采购某单一云服务的初创或中型项目 |

## 模块三：精选 GitHub 开源项目参考
1. **[transloadit/uppy](https://github.com/transloadit/uppy)** (⭐ 28k+)
   - **架构亮点**：插件化架构（Tus 协议、AWS S3、本地拖拽、Golden Retriever 页面崩溃恢复插件）。
   - **推荐理由**：目前社区最活跃、最标准的大文件上传工具包，商业友好（MIT）。
2. **[simple-uploader/Uploader](https://github.com/simple-uploader/Uploader)** (⭐ 2.5k+)
   - **架构亮点**：极度轻量，专为分片上传、断点续传、秒传设计，支持秒传预检接口。
   - **推荐理由**：国内 Vue/React 开发者大量集成在管理后台，简单透明。
3. **[spark-md5](https://github.com/satazor/js-spark-md5)** (⭐ 4k+)
   - **架构亮点**：增量计算 MD5，极低内存消耗，配合 WebWorker 不卡主线程。

## 模块四：生产环境真实踩坑指南 (Hard-won Lessons)
1. **大文件计算 Hash 卡死浏览器 UI**：
   - ❌ **DON'T**：直接在 UI 主线程一次性读取全部文件计算 MD5（超过 2GB 会直接 OOM 崩溃）。
   - ✅ **DO**：使用 WebWorker 异步计算；或采用**“抽样 Hash 算法”**（取文件头 2MB + 中间 2MB + 尾部 2MB + 文件总大小做特征值计算），毫秒级完成预检。
2. **并发分片过多导致浏览器请求排队**：
   - ❌ **DON'T**：`Promise.all` 同时抛出上百个分片。Chrome 同域名并发请求上限仅为 6 个。
   - ✅ **DO**：设计并发控制池（Concurrency Pool），限制最大并发数为 3~6 个，失败分片指数退避重试（最多 3 次）。
3. **上传到一半用户关掉标签页**：
   - ✅ **DO**：利用 `IndexedDB` 记录已上传成功的 `chunkIndex` 列表。再次选择同一文件时读取服务端已存在分片，无缝续传。

## 模块五：落地实施建议与选型决断
- **阶段一 (MVP 推荐)**：
  - 首选采用 **Uppy** 搭配后端对象存储的 Presigned URL 直传协议，客户端利用 WebWorker 抽样 Hash 预检。
- **阶段二 (生产级加固)**：
  - 增加分片上传进度实时防抖刷新；
  - 增加长耗时任务失败监控与埋点，在服务端设置分片碎片自动清理规则（如 24 小时未合并的分片自动由 S3 生命周期规则清理）。
- **最终拍板结论**：
  > **推荐优先采用 `Uppy` 方案**。兼顾协议标准化（Tus / S3）、崩溃自愈和开源生态活跃度，能节约 80% 自研分片状态机的开发与避坑成本。
